    <p>
        An exploration of how Globus could support controlled data sharing with external collaborators
        as part of the broader Guardians ecosystem.
    </p>

    <p>
        This work proposes a Globus-based architecture for collaboration scenarios where data needs to
        be exchanged in a way that is structured, scalable, and easier to govern. The design is based
        on Globus concepts such as endpoints, storage gateways, mapped collections, and guest
        collections, and adapts them into a sharing pattern suited to our needs.
    </p>

    <p>
        As part of this investigation, we also developed a starter kit for the API-focused exploration.
        That repository captures a more implementation-oriented outcome of this work, showing how key
        Globus concepts such as gateways, mapped and guest collections, service credentials, roles, and
        ACL-based access control can be configured in practice.
    </p>

    <h2>Proposed sharing model</h2>

    <p>
        The proposed model follows an <strong>always-pull</strong> approach, where data is exposed in
        a controlled location and pulled by the receiving party. This is intended to support both
        one-off sharing of a defined dataset and longer-running program sharing where data is exchanged
        over time within an agreed scope.
    </p>

    <p>
        In both cases, sharing is expected to be mediated by an explicit agreement between the parties.
        This does not necessarily imply a single formal mechanism, but there should be a clear shared
        understanding of what is being exchanged, who can access it, and under what conditions.
    </p>

    <p>
        A one-off share suits cases where a specific delivery needs to be made once, while program
        sharing supports longer collaborations that need a stable and repeatable sharing arrangement.
    </p>

    <h2>Architecture and naming</h2>

    <p>
        A key part of the proposal is the use of a structured architecture together with a consistent
        naming convention. This convention carries the mapping between the proposed sharing model and
        the Globus structures used to implement it, and is designed to support the model in a way that
        is easier to manage, understand, and trace across platforms, collaborators, and agreements.
    </p>

    <p>
        In the proposed model, a Globus endpoint would be deployed on each platform where sharing needs
        to occur, with endpoint names following the pattern <code>CCGCM-&lt;Platform&gt;</code>. Each
        endpoint would contain a default mapped collection named
        <code>CCGCM-&lt;Platform&gt;-DataDock</code>, which would act as the home for one-off sharing.
        Single exchanges would then be exposed through guest collections under that mapped collection,
        with names such as <code>&lt;OrgCode&gt;-AGR&lt;YY&gt;&lt;NNN&gt;-S</code>, linking the share to
        the collaborating organisation and the agreement that defines it.
    </p>

    <p>
        For longer-running program sharing, the same convention is used to map the collaboration model
        onto Globus resources more explicitly. Dedicated mapped collections would be created for each
        program arrangement, with names that capture the platform, gateway context, organisation, and
        agreement, for example
        <code>CCGCM-&lt;Platform&gt;-&lt;GatewayCode&gt;-&lt;OrgCode&gt;-AGR&lt;YY&gt;&lt;NNN&gt;-P</code>.
        Guest collections and share units within those mapped collections would then follow the
        agreement-defined collaboration structure, commonly aligned to projects or sub-projects.
    </p>

    <p>
        In this way, the naming convention does more than label resources: it expresses how the
        proposed sharing structure is realised in Globus. Endpoints map to platforms, mapped
        collections map to the main sharing surfaces, and guest collections map to specific sharing
        arrangements governed by agreements. While the exact naming details may evolve as the design is
        refined, consistency and traceability are central to the proposal.
    </p>
