## Requirements Gathering

### CL and AP (brainstorming)

#### Dynamism

AP:
I think we can emphasise the dynamic nature of genomics compute. It even took the AWS people
a while to get across this concept. For genomics we don't just want compute/memory - we
need to be able to summon 16 CPUS with 1GB of memory for 1 hr - then change to a single
CPU machine with 128 GiB of memory - then fan that out to 23 machines - with 1 CPU/1GiB. And
we want to do that once a week - for 100 samples - at random times
But we don't want to pay for those machines when we aren't using them
Do you disagree with that as a premise? Any clarifications?

CL:
100% agree. It's got to behave like AWS Batch or GCP PAPI v2 (or whatever that's called now)
If it's HPC-backed, there's got to be something like ABLES that allows ad-hoc use
In HPC world - how do we deal with this dynamism (me having never logged into a HPC)
I commented on this above. For HPC, the resources have to be available through a scheme like ABLES, as opposed to a merit allocation scheme (apply 6 mos in advance)
The institute itself statically decides on the size of the cluster.. but do the researchers get dynamic CPU/mem stuff for a single nextflow pipeline run?
Or do they allocate out CPUS/mem to research groups (and essentially partition up the cluster)

#### Custom Compute

CL:
Large, fast (SSD) scratch is I think a pretty common ask. Some tools create heaps of temp files that you don't want to be writing to network disk.
AP:
Access to GPUs, FPGAs, weird scale machines..
So not saying we are unique - but definitely need compute types that are not standard 2 CPU/8 GIB windows box


#### Ability to access large datasets

AP:
Terabytes of data, preferably not copied into each research space, but made available.
Data is controlled though - noone is suggesting staging a terabyte of random data
off the internet. The "blah dataset" from EGA can be trusted at a broad level
without requiring someone to inspect every byte.
"The ability to stage large controlled genomics datasets near to the TRE compute"
It is possible the large data might be need to be on-demand or cached from the perspective
of the workloads (i.e. something in the environment may need to reach out dynamically
over the internet rather than keep 1 TB of data at the tre for months at a time)

#### Workflow engines

CL:
Absolutely necessary in practice; the question is how much TRE-native support/integration
one should aim for here. Does it look like  providing managed Nextflow / Cromwell / ... services,
or just the means to stand those up in the env (e.g the Ronin model)

AP:
Genomics jobs are not something that you can do just by running a single binary or script (see 1. DYNAMISM) - the availability of workflow engines that can orchestrate this is important
I mean I think we share this with many other science fields - but possibly not the science fields that are traditionally in TREs (run excel, draw chart)

#### Complex iterative development

AP:
Genomics jobs require pipeline stages that traditionally are off the shelf containers
or pre-packaged source - but even the bespoke workflow that ties them all together
is not something that you can copy/paste in notepad. Researchers need to ability
to use some form of best practice source control to work on the jobs,
and reasonably quick turnarounds on edits.

#### Cost model

CL:
It's not unique to genomics but the scale of the data and compute needed does
make it especially pointy. Data custodians in particular need to know who is on the hook for what.
Noone is getting pinged for the egress fees of an excel - but for us possibly ouch (edited)
It also ties in with (1).. we can't afford to say 6 months in advance - here are the precise
machines we want to use for 1 year - and have the TRE provider go and provision those.




### MM (brainstorming)

- “You must understand the risk appetite of your TRE organisation.”   I think this is an interesting point when it comes to the mismatch between users of a TRE, i.e. researchers and the data access and control expectations. The more locked down the data is, the harder it will be to use, which goes against what users may expect or be used to. I’m not sure where this point lands for genomics specifically.
- “You must audit your TRE organisation against relevant requirements and standards.”   There might be specifics required for genomics labs to get TREs accredited, if that’s even an eventual use-case down the track?
- “Your TRE should be accessed via a user interface accessible using commonly available applications.”   I think there’s an interesting discussion around how users are able to log in to TREs, which is also related to the usability of them. Do they have to log in to specific networks/VPCs to access, or use specific computers/hardware? Or do we just allow users access via a web portal using regular JWT/auth methods?
- “You should understand the availability and uptime guarantees of any providers that you rely on.”   For genomics, this would be a different kind of guarantee to other fields. I think genomics might have more infrequently used computing, that should be reliable for the time that it’s running, but is allowed to be off or have long periods of downtime.
- “You must not allow users to copy data out of your TRE via the system clipboard.”   Possibly this is not as relevant to genomics? Nobody will be copying BAM files, but it might be good to enforce anyway. Although, as a general thought, what kind of data would be in the genomics TRE? I imagine it wouldn’t be directly personally identifiable (e.g. names), as the TRE would be used to run workflows?
- “You must not give anyone access to datasets without agreement from the Data Controller.”   How would this look in contexts where results get published or get shared more broadly? This point doesn’t conflict with just noting.
- “Your TRE could offer physical protection measures against data leakage or theft via physical means.”   Not sure how relevant this is for Cloud providers, as they would handle that, but would be important to consider for on premises compute.
- “You should keep backups of data and research environments, provided that this is permitted by law.”   I think this is important, but I think it should be implemented with consideration for data storage costs involving large genomics files, as there would be requirements for data storage to avoid unnecessary duplication. What kind of data would be backed up, just results, or all input files and runs?
- “You could create a semi-automated system for checks on common research outputs.”   More generally, I think there should be a discussion on what is allowed and is not inside the TRE. Inputs and outputs would need to be approved, but it’s not clear which parts of this would be automated. I think some things could be semi-automated, e.g. allowed nextflow workflows that are known to be okay, etc.
- “You must ensure that all projects using your TRE are aware of any associated costs and are able and willing to pay them.”   Costs can be quite large, and sometimes unexpected for certain workflows, especially in cloud environments, so I think this would be important for genomics. Datasets can have large storage costs and compute can have unique constraints for high performance in the moment, followed by long periods of downtime.
- “Details of TRE operations, data available and projects which have accessed the data should be publicly available (*optional for TREs without personal data).”   Are there any instances in genomics where TRE projects need to be privately run?

### CSIRO Summary

CSIRO have created a TRE called [TRECA](https://digitalonehealth.csiro.au/treca/). From their requirements document we have extracted high-level
requirements for reference across other requirements gathering exercises.

#### Generic

| Requirement                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------------------------------------- |
| Encryption at rest                                                                                                                        |
| Encryption in transit                                                                                                                     |
| Rate limiting of API surfaces                                                                                                             |
| Standard web security standard (OWASP etc)                                                                                                |
| Audit logging                                                                                                                             |
| Access control                                                                                                                            |
| Long running actions must show progress in user-interface form, ETAs and cancelability where appropriate                                  |
| Test QC processes on the overall solution i.e. it must be possible for vendors and clients to confirm the correct operation of the system |

#### Clinical

| Requirement                                                                                     |
| ----------------------------------------------------------------------------------------------- |
| Integrate with primary and secondary analyis                                                    |
| Must provide a variety of gold standard tools to run on variants (e.g. VEP)                     |
| Must perform tertiary analysis all the way to final clinical report                             |
| Must allow auditable annotations and comments on artifacts like QC metrics etc                  |
| Must provide a historical lens over previous tertiary cases                                     |
| Must link tertiary analysis through to viewing of original aligned read data in cloud           |
| Must provide customised but static variant analysis pipelines (e.g. PGx report) that can be run |
| Must perform QC pipelines and reports                                                           |

#### Data Portal

| Requirement                                                                                     |
| ----------------------------------------------------------------------------------------------- |
| System must provide multiple types of data across NGS bulk files to health records |
| System must provide a system to deidentify data (remove PII) as it moves into the data portal |
| Users must provide an interative compute environment (a virtual environment) |
| Users must be able to see statistics about the data usage and capacity of their virtual environment |
| Users can install tools into their virtual environment |
