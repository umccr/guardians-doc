## Overview

One of the researcher environments that we want to enable for researchers is
[Seqera Enterprise](https://docs.seqera.io/platform-enterprise/).

We have been assigned a Seqera organisation within the Australian BioCommons [instance](https://www.biocommons.org.au/seqera-service),
and want to reliably setup workspaces and AWS accounts to enable reserachers to do their
work. The researchers span different projects and research groups - so we need to be
flexible in the number of workspaces and AWS accounts we create (i.e. we do not just
have one).

As Terraform is our main infrastructure tool for base AWS configuration, we
decided to approach the problem
of setting up these environments using Terraform.

The main purpose of this Terraform guide is to show how we unify the construction
of an AWS environment
with a corresponding Seqera workspace.

We will step through each of the terraform scripts in our example project with some
explanatory text. The complete project is available
[here](https://github.com/umccr/guardians-doc/tree/main/example-projects/seqera-aws-terraform).

## Base Terraform

The basic configuration of Terraform for our setup will require three providers.
One is used for some time operations (e.g. "wait 5 seconds"),
and the other two allow us to control
resources from AWS and Seqera respectively.

<Code code={terraformTf} lang="terraform" title="terraform.tf" />

We have not configured any particular backends here - so Terraform state will be
written into the same folder as the Terraform files. For an example project, this is adequate,
but for production use cases other state backends should be introduced.

Our first problem is that we need to safely give Terraform permissions in our Seqera environment
to use the API - through the use of a bearer token. There are many approaches to
secret management in Terraform - in our case here we will use a Terraform variable
and pass the values in via environment variables. This should all be done out-of-band
(so no checking this into GitHub!)

```bash
export TF_VAR_seqera_server_url="https://seqera.services.my.org/api"
export TF_VAR_seqera_bearer_auth="eyJ0aWQ...="
export TF_VAR_seqera_org_id="123456789"
```

The variables that we can use to configure all the settings in our examples can
also be introduced by environment variables - or left at a default (where present).

At this point we would be able to use Terraform to deploy a workspace. To see
what would happen now (this will not actually produce resources so
feel free to execute this!) - we can `init` and `plan`. We imagine
that `dev` is the AWS profile for the account we want to operate in (adjust to your
AWS configuration).

```bash

```

## Base AWS Setup

Our first task in AWS is to set up the network in which AWS activity will take place.

This could obviously be as complex as one might want but for our example we
create a simple VPC with two public subnets.

We also add in gateways that will mean that access to S3 and Dynamo will
go direct to AWS rather than via the Internet (this is optional but costs nothing
and is generally considered best practice).

<Code code={awsVpcTf} lang="terraform" title="aws-vpc.tf" />

We then need to define the security groups that will wrap all our compute. In our
case we have no need to connect _into_ the workflow compute nodes - so we will set it
up to allow egress only. We have chosen public subnets - this avoids the need
for a standing cost of a NAT gateway - and with the security group settings below
is no less secure for the types of jobs that are run by Seqera.

<Code code={awsSecurityGroupTf} lang="terraform" title="aws-security-group.tf" />

The Seqera control plane (and web user interface) is given access to an AWS user
that helps it perform operations in the target account. This user is responsible
for creating the actual compute environments ("forging the Batch environments", hence
the name Batch forge).

This user also performs operations that show the content of buckets in the user
interface, so we give it specialised permissions to allow it to
see only designated buckets in the AWS account.

The policy here feels quite complex and verbose - but is documented directly
in the Seqera documentation. Representing it here in Terraform means that for
more complex scenarios it could be tightened as a policy. For instance, we
could introduce variables at a stack level like "wantsToUseEfs", and if the
researcher is not going to use EFS we could remove all AWS permissions
for EFS from the policy.

<Code code={awsIamUserTf} lang="terraform" title="aws-iam-user.tf" />

Seqera will require a working bucket in order to maintain state between stages
of running pipelines. Here we show an example of how we can set up a
bucket that is restricted to *only* the specific user we created above, meaning
the workspaces in the same AWS account cannot see each others work.

This may of course may be overkill for many research groups - in which case
just a plain S3 bucket with no policy statement would work fine.

<Code code={seqeraWorkingBucketTf} lang="terraform" title="seqera-working-bucket.tf" />


Finally, we need to create an access key - as this is the mechanism that Seqera
uses to authenticate with AWS. We will use these credentials later to bind
the Seqera workspace into our AWS permissions.

<Code code={awsIamAccessKeyTf} lang="terraform" title="aws-iam-access-key.tf" />

A little snippet helps delay the creation of any Seqera resources until

## Seqera Itself

We start our configuration of Seqera by creating a workspace. The workspace is
an area that the user selects from the Seqera user interface - and represents
a collection of pipelines and results.

<Code code={seqeraWorkspaceTf} lang="terraform" title="seqera-workspace.tf" />

In order to provide the workspace with access to compute and storage - we need
to give Seqera a mechanism to access AWS. To achieve this, we add a set of
Seqera credentials - taking their key/secret from the IAM user we made in
AWS portion of the setup.

<Code code={seqeraCredentialsTf} lang="terraform" title="seqera-credentials.tf" />

The main Seqera resource that we now create is the compute environment - and this is
where our combination of AWS and Seqera in a single Terraform comes to the fore.

Rather than manually creating compute environments by copy/pasting values from
the AWS console - we can directly share the values from the VPC and security
group into this compute environment resource.

Note that another advantage of representing this setup in Terraform is that decisions
like `max_cpus` (which is a big factor in potential cost to researchers) can
be documented as part of creating the Terraform. Furthermore,
researchers can ask for increases to this value by raising a change request 
on this Terraform source - all of which is activity that is auditable
and retains a history of reasons/discussions.

<Code code={seqeraComputeEnvironmentTf} lang="terraform" title="seqera-compute-environment.tf" />

## Conclusion

Terraform providers for Seqera and AWS allow us to easily and repeatably
deploy Seqera workspaces. By combining the definition of the AWS networking
with the Seqera definitions - we create workspaces that require no clicking
or copy-pasting in the Seqera user interface. Administrators can use tools
that they are familiar with to create entirely customised Seqera workspaces
for researchers.
