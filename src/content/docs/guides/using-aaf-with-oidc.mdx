This guide shows how to register an Australian Access Federation (AAF) OpenID Connect service and connect it to a backend-owned login flow.

Use this guide when the frontend should start login, but the backend should hold the AAF client secret, exchange the authorization code, create the application session, and return only local session state to the browser.

## Before You Start

Have these ready:

- AAF login access.
- Permission to register a service for an AAF subscriber organisation.
- `uv` installed for the local Python workflow.
- The URL where users start login.
- The backend callback URL that AAF redirects to after login.

For the local demo:

```text
URL: http://localhost:5000/
Redirect URL: http://localhost:5000/auth/callback
```

## 3. Register the Local Demo Service

The registered AAF service represents the backend OIDC client. The frontend is still where users start, but the backend is the component that stores the secret and handles the callback.

For the local demo, fill the form with:

```text
Name: OIDC Demo App
Description: A minimal local OpenID Connect demo application for testing AAF login with University of Melbourne users.
URL: http://localhost:5000/
Authentication methods: Secret
Redirect URL: http://localhost:5000/auth/callback
Organisation: The University of Melbourne
```

Use **Secret** because the Flask backend can store the client secret safely. Do not put the secret in frontend JavaScript.

## 5. Confirm the Required Scopes

Open the registered service and check the **Scopes** tab.

For the local demo, allow:

```text
openid profile email
```

Those scopes are enough for the backend to receive a stable subject identifier, basic profile claims, and email when the user's home organisation provides those attributes.

## 6. Configure the Local Backend

The Flask backend is the OIDC Relying Party. It starts the AAF redirect, handles the callback, exchanges the authorization code for tokens, reads user claims, and creates the application session cookie.

Dependencies are declared in `backend/pyproject.toml`, so `uv` manages the local Python environment on first run.

```toml
[project]
dependencies = [
    "authlib",
    "flask",
    "python-dotenv",
    "requests",
]
```

Create local configuration:

```bash
cd example-projects/aai-aaf-python/backend
cp .env.example .env
uv run python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Fill in `backend/.env`:

```text
FLASK_SECRET_KEY=<generated-secret>
AAF_CLIENT_ID=<identifier-from-aaf>
AAF_CLIENT_SECRET=<secret-from-aaf>
AAF_DISCOVERY_URL=https://central.test.aaf.edu.au/.well-known/openid-configuration
AAF_REDIRECT_URI=http://localhost:5000/auth/callback
```

The backend loads those values before Flask starts:

```python
load_dotenv()

REQUIRED_ENV_VARS = [
    "FLASK_SECRET_KEY",
    "AAF_CLIENT_ID",
    "AAF_CLIENT_SECRET",
    "AAF_DISCOVERY_URL",
    "AAF_REDIRECT_URI",
]
```

Register AAF with Authlib using the discovery URL and requested scopes:

```python
oauth.register(
    name="aaf",
    client_id=config["AAF_CLIENT_ID"],
    client_secret=config["AAF_CLIENT_SECRET"],
    server_metadata_url=config["AAF_DISCOVERY_URL"],
    client_kwargs={"scope": "openid profile email"},
)
```

Start login by redirecting the browser to AAF:

```python
@app.get("/auth/login")
def login():
    return oauth.aaf.authorize_redirect(config["AAF_REDIRECT_URI"])
```

Handle the callback by exchanging the code and storing minimal claims in the session:

```python
@app.get("/auth/callback")
def auth_callback():
    token = oauth.aaf.authorize_access_token()
    userinfo = token.get("userinfo") or oauth.aaf.userinfo(token=token)

    session["user"] = {
        "sub": userinfo.get("sub"),
        "name": userinfo.get("name"),
        "email": userinfo.get("email"),
        "preferred_username": userinfo.get("preferred_username"),
    }

    return redirect("/?view=protected")
```

Run the backend:

```bash
uv run app.py
```

Open:

```text
http://localhost:5000
```

## 7. Configure the Local Frontend

The frontend HTML lives in `backend/templates/index.html` and is served by Flask at `GET /`. Because the browser and the API share the same origin, there is no cross-origin setup required.

Start login with a browser redirect. This keeps the OAuth flow out of frontend state:

```js
function startLogin() {
  window.location.href = "/auth/login";
}
```

Use relative paths and `same-origin` credentials for API requests so Flask can read the session:

```js
async function fetchMe() {
  const response = await fetch("/api/me", {
    credentials: "same-origin",
  });

  return response.json();
}
```

## 9. Troubleshoot the Local Demo

Check these first if login fails:

- The Redirect URL in AAF exactly matches `AAF_REDIRECT_URI`.
- The test service has finished provisioning.
- The backend has the current client identifier and secret.
- The backend requests only scopes allowed for the service.
- Frontend fetch calls use `credentials: "same-origin"`.
- The Flask session cookie is not blocked by browser settings.

## Discussion: Deploying Beyond the Local Demo

The local setup above should stay small. Treat cloud deployment as a separate design decision because it changes URLs, secrets, cookies, CORS, monitoring, and the AAF registration.

### Production URL Shape

Choose stable HTTPS URLs before registering a production AAF service.

The simplest approach keeps frontend and backend on the same domain, the same way the local demo does:

```text
URL: https://app.example.org/
Redirect URL: https://app.example.org/auth/callback
```

Then update backend configuration:

```text
AAF_DISCOVERY_URL=https://central.aaf.edu.au/.well-known/openid-configuration
AAF_REDIRECT_URI=https://app.example.org/auth/callback
```

If you later separate the frontend to its own CDN origin (for example S3 + CloudFront at `https://app.example.org` with the API at `https://api.example.org`), that becomes a cross-origin deployment. You will need to add `flask-cors` back, configure `CORS(app, origins=["https://app.example.org"], supports_credentials=True)`, and switch fetch calls back to `credentials: "include"`. Register the public frontend URL in AAF as the service URL and update `AAF_REDIRECT_URI` to the API callback.

### Backend Deployment Notes

On AWS, a typical backend path is ECS Fargate, App Runner, Elastic Beanstalk, or Lambda behind API Gateway if the Flask app is adapted for Lambda. Put it behind HTTPS using ACM with an Application Load Balancer, CloudFront, or API Gateway.

Store these values outside the image and inject them at deploy time:

```text
FLASK_SECRET_KEY
AAF_CLIENT_ID
AAF_CLIENT_SECRET
AAF_DISCOVERY_URL
AAF_REDIRECT_URI
```

Use AWS Secrets Manager or SSM Parameter Store for `AAF_CLIENT_SECRET` and `FLASK_SECRET_KEY`. Build from `backend/pyproject.toml`; once dependency versions are final, commit and deploy with `uv.lock`.

For Google Cloud, the equivalent options are Cloud Run, App Engine, or GKE with secrets stored in Secret Manager.

### Frontend Deployment Notes

When Flask serves the frontend (the same-origin approach), the HTML in `backend/templates/index.html` is deployed with the backend container. On AWS that is ECS Fargate, App Runner, Elastic Beanstalk, or Lambda with a web adapter. On Google Cloud that is Cloud Run or App Engine.

The frontend uses relative paths, so no URL configuration is needed:

```js
window.location.href = "/auth/login";

await fetch("/api/me", { credentials: "same-origin" });
```

Do not store AAF access tokens, ID tokens, or the AAF client secret in browser storage.

### Cookie and CORS Notes

For production HTTPS, update the backend session configuration:

```python
app.config.update(
    SESSION_COOKIE_HTTPONLY=True,
    SESSION_COOKIE_SAMESITE="Lax",
    SESSION_COOKIE_SECURE=True,
)
```

No CORS configuration is needed when the frontend is served from the same origin as the API. If you later move the frontend to a separate CDN origin, add `flask-cors` and configure CORS as described in the production URL shape note above.

### Production AAF Registration

Register production only after the public URLs are stable.

1. Open [AAF Production Federation Manager](https://manager.aaf.edu.au/dashboard).
2. Register a new OpenID Connect service.
3. Use the production application URL as the service URL and the callback as the Redirect URL.

```text
URL: https://app.example.org/
Redirect URL: https://app.example.org/auth/callback
Authentication Methods: Secret
Organisation: <your AAF subscriber organisation>
```

Copy the production Identifier and Secret into the production secret store, allow the required scopes, and wait for organisational or AAF approval before testing production login.

### Operational Notes

Before handing the service to users:

1. Record the AAF service name, owner, redirect URIs, and scopes.
2. Record where `AAF_CLIENT_SECRET` and `FLASK_SECRET_KEY` are stored.
3. Document who can rotate the AAF secret.
4. Add a smoke test for `/auth/login`, `/auth/callback`, `/api/me`, protected routes, and logout.
5. Keep only minimal claims in the local application session.
